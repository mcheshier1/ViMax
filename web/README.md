# ViMax Web

The Film workbench uses the existing ViMax agent loop and JSONL event stream. The browser makes review and generation scope explicit; the agent still executes planning and rendering.

From the `ViMax` repository root, create the private local agent configuration once:

```bash
cp configs/agent.example.yaml configs/agent.local.yaml
```

```bash
cd web
npm install
npm run dev
```

Or from the repository root:

```bash
./vimax web
```

The default address is `http://127.0.0.1:4173`. Override it with `VIMAX_WEB_HOST` and `VIMAX_WEB_PORT`.

Production mode:

```bash
cd web
npm run build
cd ..
./vimax web start
```

Agent credentials continue to come from ViMax environment variables or `configs/agent.local.yaml`.

## Film workbench

- **Film** is the default destination. One reel row represents one shot in playback order; select its first frame, last frame, or clip in the persistent viewer.
- **Assemble** stitches the existing accepted clips in camera playback order into `final_video.mp4` using local FFmpeg only, then opens **Final film** for review. Every active clip must still match its approval fingerprint; removed shots are excluded. Save or discard local film drafts first. Assembly does not call the assistant or a media provider, change render settings, overwrite clips, or alter clip/keyframe approvals. Inputs are normalized to 1280×720, 30fps H.264/AAC, with silence for clips without audio; unchanged ordered inputs reuse the existing assembly. Failed encoding or publication preserves the previous final and its approval. A new final film awaits its own approval. `ffmpeg` and `ffprobe` must be available on the server (`VIMAX_FFMPEG_CMD` and `VIMAX_FFPROBE_CMD` may point to alternate executables).
- The video player's **Download** saves the final film as `<project title>.mp4` (or `<session ID>.mp4` for an unnamed project). Unicode titles are supported; characters unsafe in filenames are replaced. Other artifacts retain their original filenames. Download naming does not rename stored files or change approvals.
- **Needs review**, **Needs changes**, and **Missing** narrow the reel. **Accept & next** advances only after approval is saved. Review requires the first frame for HeyGen Video 1 and both frames for the other presets; accepted output must be unlocked before regeneration.
- The assistant refreshes saved approval records and their artifact fingerprints at the start of each turn. This current state overrides historical refusals and summaries; the renderer still enforces the actual review gates. Accepting stills in Film does not require restarting the agent or accepting them again.
- **Restart shot…** beneath the selected shot inspector opens a file-list confirmation. It removes that shot’s generated frames, clips, cached prompts/selectors, held redraw backups, and affected assembled films; clears its frame/clip approvals; and invalidates continuous successor approvals and final-film approval. The saved editable plan/brief, camera placement, shared portraits/set references, and other shots’ media are preserved. Save or discard the targeted shot’s local drafts first. Running/queued work, unsafe paths, and changed confirmation fingerprints refuse the reset; persistence failures roll back all removals. The reset cannot be undone after success and never generates media or starts the assistant. Edit the retained plan as needed, then explicitly generate stills, review/accept them, and request the clip.
- The shot inspector shows **Shot brief**, **First frame description & characters**, **Last frame description & characters**, and **Motion description** inline. Each has an explicit **Edit …** control. Frame editors also toggle visible characters. **Cancel … edits** restores only that editor’s saved fields; other drafts and feedback remain protected. **Save plan** explicitly confirms approval invalidation and saves all changed guidance without generating media. Brief edits update the storyboard and cached shot description (plus an existing per-shot brief); motion edits update the description used in the clip prompt. Drafts persist per project, render root, and slot in browser storage, including across reloads; older frame-only drafts remain protected, and fields never save on blur. **Edit feedback** is separate, and existing feedback is retained as a protected draft when a plan is saved. **Save & regenerate** saves guidance, then opens a generation decision rather than immediately starting a render. New backend guidance fields require an idle bridge restart before deployment.
- Frame descriptions remain editable when the assistant is connected but idle, even if an earlier render left a `rendering` status behind. Active/queued requests and pending generation still disable edits. An accepted frame does not need a separate unlock to edit its description: **Save plan** confirms and invalidates approvals. **Prompt sent for this frame** is a read-only record of the previous provider request, not the editable description; regenerate from saved guidance to build a new prompt.
- While the agent is busy or a render is active, Film shows an explicit notice explaining that editing, generation, and approval actions are temporarily disabled. Shot browsing remains available, and **Open Assistant** opens the current work. Missing-frame warnings separately explain that frames must be generated before acceptance.
- **Generate…** shows the phase, exact shot slots, selected model/provider, and estimated or unknown cost. Selected, missing, and needs-changes scopes do not include accepted outputs. Clip generation requires accepted frames. Global model changes require a new decision; video settings saved here affect future renders in every project. The workbench does not automatically retry failures.
- **Shot duration (seconds)** in the inspector changes an individual clip's requested length. First configure and save **Settings → Video generation → Maximum shot duration for this model**; until then the shot control stays disabled. Limits are remembered separately for each provider/model. The default is 8 seconds where supported, with a compatible model default otherwise; **Default shot duration** in Settings controls shots without an override.
- Known models offer only supported whole-second durations within the configured maximum, including discrete choices and resolution-specific LTX limits. Yunwu's installed adapter supports only 8 seconds. Custom-model maxima require checking the provider's duration support. The shared catalog is `configs/video-duration-models.json`; LTX limits follow the [2.5](https://docs.ltx.video/models/ltx-2-5) and [2.3](https://docs.ltx.video/models/ltx-2-3) support matrices, and Agnes follows its [2.5](https://www.agnes-ai.com/en/docs/agnes-video-v25) and [Flash](https://www.agnes-ai.com/en/docs/agnes-video-25-flash) documentation.
- A duration-only **Save plan** preserves keyframes and their approvals, other shots, and cached media. It invalidates only that shot's clip approval, final-film approval, and coverage review. **Save & generate clip…** opens a video-only scope/model/cost decision; it does not redraw frames or start generation automatically. The decision lists each targeted shot's duration and sums them for the estimate. Incompatible overrides after a model change are rejected, not silently clamped.
- Overrides persist as `duration_seconds` in `shot_description.json`; choosing **Default** removes the override. New shots inherit the default rather than copying a neighbor's override; restarting an existing shot retains its override. Saving model settings is blocked while agent work is active or queued, so changing duration limits cannot cancel a running generation.
- The generation decision distinguishes missing shot-to-set assignments from unapproved references. If a shot has no location assignment, use **Edit first frame**, choose its location set(s), then **Save plan** before reopening generation. Approving a set in Assets does not assign it to a shot.
- Submitting a new generation replaces historical failure/stall banners with **Generation request sent — waiting for the agent**. Once fresh render progress arrives, the indicator changes to **Rendering**. Errors from the new attempt remain visible; old records are not deleted from Activity. Waiting, failure, and stall notices include **Open Assistant** for direct access to the agent response.
- **Script coverage** can remain collapsed even when it needs attention; its warning summary stays visible. Reviewing coverage is an explicit language-model request, not media generation.
- **Assistant** and **Activity** open as drawers. Assistant requests can target the whole film or selected shot. Chat drafts and attachments stay with their project while switching projects. Opening or switching existing projects does not start the agent; sending a request does. Creating a project explicitly starts the agent to create its session, so **Create** is disabled while any project has active or queued requests. The server also rejects agent replacement with HTTP 409 until that work finishes; it does not cancel the current request.
- While the assistant works, the composer remains editable and **Queue message** submits follow-ups in order. Messages show **Queued**, **In progress**, then **Answered**; each captures its shot/film scope and attachments at submission. Failed sends preserve the draft and attachments without stopping the current request. Switching the viewed project does not interrupt work; sends to a different project are blocked until the current request finishes.
- **Script** displays story documents. **Assets** displays thumbnails and video posters; raw JSON is behind the Advanced disclosure. Project details, settings, uploads, and project deletion remain available.
- **Generate asset…** in Assets opens the asset-creation dialog. Still previews offer **Generate asset from this still…** with the image preselected; set and character cards offer **Generate alternative…** with their destination preselected. Choose a project image or a device image (picker or drag-and-drop), asset type, and a new or existing destination. Optional crop controls preview the selected region without modifying the original.
- To update a set without a model call, choose **Set → existing destination → Use uploaded image as-is** (or **Use image as-is** for project images), then **Review asset setup → Apply image to [set name]**. Apply saves the reviewed full image or crop as a PNG reference and accepts the set. Device originals are uploaded only on Apply and retained; project originals remain unchanged. Replaced references remain available as candidates. New sets can also be created and applied; assign their shots separately in Assets.
- The review shows bound shots before Apply. Applying invalidates bound-shot, linked-successor, and final-film approvals while retaining existing media; it does not regenerate shots or call a model. Saves reject stale inventories and active/queued work. On a stale-save error, choose **Edit setup → Reload destinations**, review the updated destination/impact, then Apply again. Successful saves show **Done** and refresh Assets. The applied PNG limit is 32 MB; device-original uploads retain the workspace upload limit.
- New backend endpoints require restarting the web server when the agent is idle; frontend hot reload does not reload `server.mjs`. An old backend can serve an updated dialog without its Apply endpoint. Unknown API routes return JSON errors, and the client reports the endpoint and HTTP status for empty/non-JSON responses rather than an opaque JSON parser error. Such a response does not confirm a save: check the set state before retrying.
- Character creation and **Generate from image** remain review-only. Their instructions and model controls do not execute paid generation or save character assets. Closing without Apply discards setup; after Apply, the saved set persists.

The selected project, destination, shot, preview, filter, and reel position are remembered locally. Browser storage restrictions can prevent persistence; clearing browser storage removes unsaved shot drafts.
Unchanged persisted shot records are not unsaved edits. Every saved film snapshot reconciles all loaded shot plans and feedback stages, including unselected shots: already-saved guidance and matching saved feedback are cleared from local draft tracking. Unknown drafts and genuinely different guidance or feedback remain protected. Switching between Film, Assets, and Script does not prompt or discard drafts; the Film editor stays mounted. Genuine drafts still trigger confirmation when switching projects and protection when closing the page or requesting generation.

### Shot-writing conventions

Generated storyboards, first/last frame descriptions, motion prompts, revised shots, and script-coverage suggestions use canonical character names instead of repeated appearance profiles. Internal visual descriptions retain `<Name>` tags. Shot writing uses concise present-tense, filmable action; clear location, framing, blocking, and camera movement; named speaker cues with verbatim dialogue; and short parentheticals only for essential delivery or action. Brief costume, prop, or continuity details remain when the shot needs them.

Character profiles still define portrait generation. Shot reference captions identify only the character and portrait view; explicit `Image N` bindings preserve visual identity without repeating biographies in the image prompt. User-supplied frame descriptions are preserved verbatim when bindings are added. For example: `Medium two-shot. INT. SALOON - DAY. <ALICE> stands left, facing <BOB> across the bar.` Motion: `Static camera. <ALICE> places a coin on the bar. <BOB> looks at the coin. ALICE: "Your move."`

This convention applies to newly generated or revised prompts, not automatic rewrites of cached plans or regeneration of existing media. Start a fresh agent after active work finishes to load Python prompt and pipeline changes; never interrupt a running render.


## Media and refresh behavior

`ffmpeg` must be available on the server for image thumbnails and video posters. Set `VIMAX_FFMPEG_CMD` to an alternate executable path if needed. Thumbnails are generated on demand with bounded worker concurrency and a disposable temporary cache; a thumbnail failure does not silently download the full original.

The selected preview loads the original media. Original delivery supports HTTP byte ranges and conditional requests, so clip playback can seek without downloading every clip in the reel.

The workspace shares one film snapshot across its views. Lightweight progress reads trigger fresh snapshots when the revision changes; external file changes are also reconciled periodically. Reads pause while the browser tab is hidden, pending reads are cancelled on project changes, and mutation refreshes wait for a post-save snapshot. Acceptance fingerprints remain request-scoped rather than relying on a persistent size/mtime cache.

After updating server code, restart the web server **when its agent is idle**. A frontend hot reload alone does not install the new film, progress, and thumbnail endpoints.

Agnes video generation waits indefinitely by default while the provider is at capacity or an accepted job is queued. Explicit queue/capacity HTTP 503 refusals and HTTP 429 admission refusals retry submission with exponential backoff and jitter, capped at 60 seconds. Once Agnes returns a video ID, transient status HTTP 429/5xx responses and connection/read interruptions retry **that same video ID**, never another paid creation request. Queued/running checks gradually slow to a 60-second interval; result-download interruptions retry the same result URL. Valid `Retry-After` seconds or HTTP dates set a minimum wait and may exceed the cap. Activity reports retries and emits waiting updates at least once per 60-second sleep segment.

`VIMAX_VIDEO_QUERY_TIMEOUT_SECONDS` defaults to **0 (unlimited) for Agnes**; a positive value optionally limits accepted-job polling, including its retry waits and request timeouts. Individual HTTP requests still use `VIMAX_VIDEO_REQUEST_TIMEOUT_SECONDS` (default 60 seconds). Authentication/invalid-request errors, unrelated creation failures, and terminal failed/cancelled/expired jobs stop with an error. Ambiguous submission connection failures are not automatically resubmitted: Agnes may already have accepted and charged that request. **Stop** interrupts local waiting but does not cancel an already accepted provider job. Waiting survives browser refresh, not backend shutdown/restart. Restart an idle agent to load Python adapter changes; do not interrupt active work or resubmit a paid render merely to recover its status.

## OpenRouter image models

**Settings → Image generation → Model** is a dropdown with **Qwen Image 3**, **ByteDance Seedream 5.0 Flash** (`bytedance-seed/seedream-5-0-flash`), and **Custom model…** when the image base URL is OpenRouter. Choosing Custom reveals an editable model-ID field; existing unlisted models load there without being replaced. Select a model, keep `https://openrouter.ai/api/v1` and your existing OpenRouter API key, and save. Start a fresh idle agent before generating so it picks up the saved configuration; do not interrupt an active render. Opening Settings or changing an unsaved selection does not change the stored model or regenerate existing artifacts.

The existing Images API adapter handles portraits and keyframes without a separate provider implementation. OpenRouter advertises 1K/2K output, 16:9 and portrait aspect ratios, and up to 14 input references; the adapter reads supported parameters and reference limits from the image catalog before rendering. **Seedream defaults to 1K** rather than the provider's 2K default. **Settings → Image generation → Resolution** offers 1K, 2K, or Provider default for Seedream and Qwen; custom OpenRouter tiers are validated against the catalog before a generation request. Set `image.resolution: "1K"` or `"2K"` in `configs/agent.local.yaml`; `"auto"` uses the provider default, and an omitted value uses the model default. `VIMAX_IMAGE_RESOLUTION` overrides the saved choice; Settings displays the active saved resolution. Changes apply to new portraits and keyframes only: existing assets are not resized or regenerated, and video resolution is unchanged. Restart the bridge and start a fresh agent **only after active work finishes** to load the backend changes. See the [model page](https://openrouter.ai/bytedance-seed/seedream-5-0-flash) and [image catalog](https://openrouter.ai/api/v1/images/models) for current capabilities and pricing.

**Settings → Image generation → Image editing model** saves a separate OpenRouter model preference under `image.editing_model`, defaulting to **Black Forest Labs: FLUX 3 Image Klein** (`black-forest-labs/flux-3-image-klein`). The selector also offers **Krea K3 Edit**, **Qwen Image 2.1 Turbo**, and **Custom model…**; saved custom IDs remain editable after reload. Changing the generation model or provider preserves this choice. Saving it does not run an edit, create a set, change the portrait/keyframe generation model, or regenerate existing assets.

## Provider API keys

LLM, image, video, embedding, and reranker settings remember API keys separately for each provider within each category. Switching providers selects that provider’s saved credential without overwriting the previous provider’s key or copying another category’s key. Changing only the model keeps the same credential. Custom endpoints are isolated by origin and API path.

The API-key input is deliberately blank after saving or reloading: stored secrets are never returned to the browser. **Configured** means the selected provider has a saved key. Newly entered keys remain in memory while switching providers; Save commits every nonblank provider-key draft, including drafts for providers switched away from. Blank inputs do not delete saved keys. Failed saves retain drafts; controls are locked during a save so its response cannot discard newer edits.

On the next save, existing single `api_key` settings migrate under their current provider. A key already overwritten before this change must be re-entered once. `configs/agent.local.yaml` stores each category’s bank in `api_keys`, with `api_key` maintained as the selected-provider mirror. For manual edits after migration, update the appropriate `api_keys` entry, not just the mirror. Category-specific API-key environment overrides still take precedence. Migrated image/video settings inherit an LLM key only when both effective endpoints belong to the same provider; an OpenRouter key cannot fall through to Agnes or LTX.

This update requires an idle web-bridge restart and a fresh agent process. If an older bridge lacks provider-key metadata, Settings disables Save rather than silently losing provider drafts. Do not restart during active work.

## Agnes image models

**Settings → Image generation → Provider → Agnes AI** offers **Agnes Image 2.5 Flash** (`agnes-image-2.5-flash`, recommended), **2.1 Flash** (`agnes-image-2.1-flash`), **2.0 Flash** (`agnes-image-2.0-flash`), and a custom-model field. Selecting Agnes changes the image endpoint/model and selects its saved key if configured, while preserving other providers’ saved keys. Enter your Agnes key in the image API-key field before saving if needed. Video and LLM keys are separate and are not copied automatically.

The renderer uses the Agnes Images API at `https://apihub.agnes-ai.com/v1/images/generations` for text-to-image portraits and reference-conditioned portraits/keyframes. Local references are sent as ordered Data URIs in `extra_body.image`. Text-to-image requests use `return_base64`; reference-conditioned requests put `response_format` inside `extra_body`. Both Base64 and image-URL responses are supported, and output downloads do not receive the API key. The existing landscape guard remains enabled.

2.5 and 2.1 default to `size: "1K"` with `ratio: "16:9"` (native `1312×736`); Settings offers 1K/2K/3K/4K through `image.resolution`, mapped to the provider's `size` parameter. A per-request `size` argument takes precedence. 2.0 uses its documented `1024×768` landscape default rather than undocumented tier/ratio parameters. Yunwu also exposes Provider default only because the installed Gemini SDK does not support explicit image-size configuration; unsupported explicit tiers fail before generation instead of being silently ignored. See the [2.5 documentation](https://wiki.agnes-ai.com/en/docs/agnes-image-25-flash), [2.1 documentation](https://wiki.agnes-ai.com/en/docs/agnes-image-21-flash), and [2.0 documentation](https://wiki.agnes-ai.com/en/docs/agnes-image-20-flash) for current capabilities and promotional pricing; free rates are not guaranteed permanent.

For file/environment configuration, set `image.model`, `image.base_url: https://apihub.agnes-ai.com/v1`, and `image.api_key`, or `VIMAX_IMAGE_MODEL`, `VIMAX_IMAGE_BASE_URL`, and `VIMAX_IMAGE_API_KEY`. Provider selection is inferred from the base URL; no `image.provider` field is required. Existing OpenRouter/Yunwu and custom URL/model settings remain available. Start a fresh idle agent before generating to load the new Python adapter; never interrupt active work to switch providers. An idle bridge reload also activates numeric clip-duration preservation when saving the full settings form.


## OpenRouter video models

`heygen/heygen-video-1` is available under **OpenRouter** in Settings and the Film generation decision. It uses the existing OpenRouter API key and video adapter; adding the preset does not change the currently configured model or submit a render.

- Clips support integer durations from **5 to 15 seconds**, at **480p** or **768p**. Selecting HeyGen keeps compatible values and replaces incompatible ones with 480p and an 8-second duration.
- Switching to another OpenRouter preset replaces HeyGen's 480p/768p settings and incompatible durations with compatible values. Changing providers resets the clip duration to 8 seconds alongside the provider's default model and resolution. Custom model values remain editable.
- Only the **first frame** conditions generation. The pipeline does not generate an unused end keyframe, and the workbench permits review and approval of the first frame alone. Existing end frames are retained, but cannot constrain the clip's ending. Choose a model with last-frame support when exact final poses and cut continuity matter.
- OpenRouter describes synthesized dialogue, ambience, and effects, but exposes no `generate_audio` switch for this model. The audio control is hidden; the provider's native audio behavior applies.

The [OpenRouter video catalog](https://openrouter.ai/api/v1/videos/models) currently lists these USD-per-second SKUs:

| Resolution | Output-duration rate | Reference-duration rate used for conservative budgeting |
| --- | ---: | ---: |
| 480p | $0.02 | $0.04 |
| 768p | $0.03 | $0.06 |

For an 8-second clip, the advertised output rates are $0.16/$0.24; the workbench budgets $0.32/$0.48 respectively. The applicability of the higher reference-duration SKUs to this first-frame image workflow has not been confirmed with a paid generation. Missing or unknown resolutions budget at $0.06/second. Estimates are not guaranteed charges; prices and additional provider charges can change.

Capabilities are validated against the catalog before submission. Unsupported last-frame and audio-toggle parameters are omitted with progress notes; invalid duration, resolution, or aspect ratio fails before a job is created. OpenRouter origin-relative polling URLs retain their leading slash so the API prefix is not duplicated. See the [model page](https://openrouter.ai/heygen/heygen-video-1) for current availability and capabilities.

## Deleting assets

- Open an image or video in **Assets**, then click **Delete asset** directly below the preview header. The confirmation shows the exact session-relative file and dependency impacts. **Cancel** preserves everything; **Delete asset permanently** removes only that media file and refreshes the gallery.
- For bulk deletion, use the checkbox on each image/video tile, **Select all shown**, or **Clear selection**. **Select all shown** adds only the current filter's visible tiles. Selection survives filter changes, with a hidden-selected count, so review the complete path list under **Delete selected** before confirming **Delete N assets permanently**.
- Bulk deletion validates every file and dependency revision before one locked transaction. If any member is missing, unsafe, stale, or busy, none are deleted; transaction failures restore prior media and metadata. **Cancel** and failed requests retain the selection, and **Refresh deletion plan** prepares a fresh confirmation. Success clears selection and refreshes the gallery. Switching projects clears selection; externally removed items are pruned.
- Deletion is irreversible. Sibling views, saved prompts, shot plans, and other media remain on disk. An unreferenced archive or old-model asset leaves live approvals unchanged. Deleting a selected portrait view removes matching registry references, makes that set incomplete, and invalidates affected portrait and dependent output approvals.
- Deleting active keyframes, clips, or media used by recorded frame references invalidates the relevant approvals and final-film approval; chained successors are invalidated where applicable. Dependent media is preserved, not cascaded away. No generation is triggered; a later explicit render may regenerate missing required media.
- Confirmation revisions bind the file contents and dependency metadata. Stale confirmations must be refreshed; unsafe paths, symlinks, non-media files, busy project locks, and running or queued project requests refuse deletion. An idle connected agent does not block single or bulk deletion. Live work state is checked under the project write lock and again before mutations. Server changes require an idle bridge restart before these endpoints are available.

## Set references

**Set reference** (or **location reference**) is the location-design image; a backdrop usually means scenery, and a set piece can mean a major staged sequence.

- **Assets → Sets**, beside Characters, owns location descriptions, default shot assignments, generation, and approval. For a western, describe the empty saloon's layout, bar, doors, tables, props, and lighting; save it, then request its image on that card.
- Text planning prepares locations from the actual source and planned shots. For an older project without them, **Prepare set plan (text only)** requests explicit text-only planning; it does not authorize images or clips. **Add set** supports manually prepared locations. Shots without an explicit override need matching default assignments before new image generation.
- On each saved set card, click **Request 1 image for [set name]** to generate one alternative for that set only. Review the configured model, exact project style, and unknown provider cost before clicking. Request another image separately if you want another option; there are no batch-selection checkboxes or candidate-count controls. This authorizes only `stop_after="sets"`, `set_ids=[that set]`, and `set_candidate_count=1`. Unsaved edits on other sets do not block the request. Empty locations do not need portrait approval and cannot advance into shots or video. Existing images require explicit scoped `redo_sets` to add another alternative; accepted references must first be unlocked.
- Set-image generation uses the saved set description, model, and style, not shot-prompt drafts. Unsaved shot drafts do not block it and are left untouched. **Save** on a set card is disabled when that set has no unsaved edits; no save is required in that case. Text-only set planning still requires saving or discarding shot drafts because it can change their assignments. Shot-frame generation retains its own draft protections.
- A request displays **Submitting…**, then a sent confirmation or submission error beside the generation controls, and opens **Activity** for the agent's progress, errors, and result. Sending is not proof of successful generation. Candidate inventory refreshes as project progress and request activity change. If a request was sent but the Assets refresh fails, the notice explicitly says so: check Activity before submitting again to avoid duplicate charges.
- Review candidate previews, full images, and their saved prompts. Click **Use this image for Saloon** to choose one, then **Approve Saloon** separately. Candidates remain available; generation never silently chooses, approves, or replaces the active image. Selecting a different image clears its acceptance and affected output approvals but keeps existing media. Selection and approval make no generation requests.
- **Use this image** works with an idle connected agent; no manual stop is required. Running or queued requests for the project block selection until they finish. The selection checks live queue state under the project write lock, so reference changes remain serialized with other writers.
- In **Film → shot editor → Edit first frame / Edit last frame**, named set buttons appear beside the character controls. Select the location, then **Save plan**. Set choices bind both frames of the shot; refer to the set by name in the description, such as “Inside the Saloon, <ALICE> stands at the bar.” Merely mentioning a name does not bind an image. Unapproved sets have a warning; new generation remains locked until their selected reference is approved.
- Shot-button choices override the descriptor's default assignments without modifying its design, image, or acceptance. Removing every set and saving records `set_ids: []`: an explicit choice to generate without location-reference images. Restart preserves this choice, so first/last stills remain eligible after a shot reset. Missing/null bindings still inherit defaults and remain blocked if no default exists. New and duplicated shots inherit the source shot's effective selection.
- Acceptance fingerprints the descriptor, PNG, and provenance against the current image model and style. Changed, missing, corrupt, rejected, or unapproved references assigned to a shot block its new and redrawn images; `allow_unlocked` cannot bypass their approval. An explicitly unbound shot is not blocked by unrelated unapproved sets. An unavailable or older backend fails closed.
- Assigned, approved references are mandatory image inputs, alongside required scene-continuity images. Explicitly unbound shots omit location images but retain portrait and continuity requirements. The renderer reserves provider capacity for mandatory inputs before selecting optional character portraits and refuses a request when mandatory inputs exceed that capacity. These are image-conditioned generations, not guarantees of pixel-identical architecture.
- Editing a descriptor or its default assignments invalidates that set's acceptance and affected frame, clip, and final-film approvals, retaining existing media. Changing a shot's set buttons invalidates that shot's output approvals without clearing the set's own acceptance. Drafts survive reloads and failed saves. Neither saving, selecting, approving, rejecting, nor unlocking initiates paid generation. Cached complete frames can still be used for video without buying new location images; nothing automatically redraws existing projects.
- Native Script, Idea, and Novel rendering use four explicit phases: `portraits`, `sets`, `stills`, and `video`, defaulting to `portraits`. Missing text plans must be prepared explicitly before media phases. Restart the idle bridge and use a fresh agent process for these backend changes; never interrupt an active render.

## Portrait cache recovery

- **Assets → Characters** lists planned characters, descriptions, workflow scopes, front/side/back availability, set completeness, and approval state. The list comes from character metadata, not the surviving image gallery: deleting every portrait leaves the character visible with missing views. Invisible characters are labeled **No portrait required**. Click an available view to open the existing preview and selection/approval controls. Planned Idea scenes share the global character set until they have their own model registry.
- For Script2Video projects, choose **Generate missing portraits** in Assets, or **Film → Generate… → Phase → Character portraits**. The confirmation lists every incomplete visible set and the configured image model; it is not an individual-character targeting operation. It authorizes only `stop_after="portraits"`, with no forced redraw or later frame/video phase. Normal reconciliation reuses surviving views and unchanged complete sets, while provenance changes can require a trio rebuild. Provider charges are disclosed as unknown.
- Missing-only generation is blocked for invalid portrait files, a configured/inventory model mismatch, unsaved film drafts, or an active request. Delete invalid media or select a valid trio first; model migration and non-Script workflows require a separate decision. Before sending, the interface rereads configuration and portrait inventory. A pending request is not automatically retried; **Clear waiting notice** only stops local tracking, not the agent or render. Newly rendered portraits remain **Needs review**, not automatically approved; every required visible set must be complete and accepted before frame generation.
- Script rendering reconciles the portrait registry against visible characters on every run, including `stop_after="portraits"`. A reusable entry requires front, side, and back regular files; missing characters, empty entries, and dangling paths are repaired rather than reported as a successful no-op.
- Model-scoped `provenance.json` records the character specification, style, and model fingerprint. Subsequent specification changes invalidate that character's owned portraits. Removing a completed character's registry entry forces regeneration even if its PNGs remain. Complete legacy entries are baselined without redrawing; changes made before provenance exists cannot be inferred retrospectively.
- Individual character failures do not discard successful characters or abandon the remaining batch. Failed runs report `status: "error"`, explicit missing portrait paths, and `failed_characters` in `render_status.json`; they do not request approval for an incomplete batch. A retry reuses saved partial views and completed characters. Valid supplied shared portraits are retained without modifying their source files.
- **Assets → Active portraits** filters to complete visible-character sets referenced by the recorded render root/model registry. Active tiles have an outline and an **Active** badge; **Accepted** is separate and requires an uninvalidated approval with matching file fingerprints. Active views are candidates for shot references, not a promise that every view is sent to every generation request. Backups are never promoted based on recency.
- Portrait previews show the session-relative file location, an **Open original** link, and saved prompt text/source. Backup view filenames are recognized too. A unique sibling `prompts*.json` can supply archived prompts; unavailable or unrecorded prompts are stated explicitly rather than reconstructed from today's character specification.
- To reuse an existing set, open any of its views in **Assets**, inspect the front/side/back trio, choose **Current character**, then click **Use this set for Claude** (or the chosen character). This copies the complete sibling set and saved prompts into that character's current model directory, updates the registry and renderer provenance, and makes no generation requests. Archived files remain unchanged; `REMOVED_` views are never mixed with unprefixed views.
- Click **Approve Claude’s set** separately to approve only that character's selected trio. Other characters remain unapproved unless they already have a valid approval. The portrait-stage approval becomes accepted only when every required visible character has a complete selected set and matching approval; Film's stage-wide acceptance still approves all complete sets together.
- Selecting different image bytes clears that character's approval and invalidates dependent keyframe, clip, and final-film approvals without deleting their media. Reselecting the identical active bytes preserves approval. Stale revisions and busy project locks refuse the mutation rather than replacing concurrent changes.
- These Python changes require a fresh agent process before the next render. Do not interrupt active generation to reload them.

## Per-shot exact frame continuity

- In **Film → shot inspector → First frame**, enable **Use previous shot’s last frame as this shot’s first frame**, then **Save plan**. The checkbox is absent for the first active shot in playback order, regardless of its numeric ID. It can reuse a predecessor across cameras or Idea scenes.
- The checkbox is a protected local draft until explicitly saved. Saving invalidates the shot's output approvals, linked successor approvals, coverage review, and final-film approval; it preserves media and makes no generation request. Cancel first-frame edits restores its saved continuity choice without discarding last-frame or feedback drafts.
- On explicit regeneration, `reuse_previous_last_frame: true` in `shot_description.json` copies the predecessor's ending image byte-for-byte instead of generating a new first image. Its description does not alter the copy. A bracketed shot still generates its own ending from that copied start, with any assigned set references approved.
- The predecessor follows actual camera playback and stored active-shot order, not shot IDs. Reordered open drafts require reconfirming a changed source before saving. A shot moved to first ignores its stored reuse flag. Generated copies record the source slot, path, and SHA256; stale copied frames require explicit redraw.
- A missing excluded predecessor ending refuses generation rather than expanding paid scope. When a selected predecessor is redrawn, reuse waits for its fresh ending, not its old cached bytes. Standard per-shot reuse additionally checks the predecessor's approval state; global chained mode treats an excluded predecessor's saved ending as an independent anchor. First-frame-only providers can copy an existing ending but cannot create a missing one; their clips do not honor end-keyframe constraints.
- This choice does not require global chained continuity. Unset choices retain the existing global mode's behavior; an explicit unchecked choice overrides its automatic same-camera byte reuse.

## Shot reference continuity

- In the standard camera renderer, a bracketed shot's first frame references the immediately preceding active shot's **last frame** with that shot's `lf_desc`. The predecessor follows `camera.active_shot_idxs`, including reordered or noncontiguous shot IDs; it is not always the camera's opening shot. Each shot's last frame still references its own first frame with `ff_desc`.
- Boundary generation waits for that predecessor image. A scoped request refuses a missing excluded predecessor rather than silently generating it. First-frame-only video models retain start-frame references because they do not produce ending keyframes.
- The source image remains a required reference even if the selector omits it. When an image is explicitly redrawn or absent, cached selections containing the wrong source image or caption are rebuilt. Existing rendered images are preserved until explicitly redrawn.
- Without per-shot exact reuse, this standard camera path is reference-conditioned generation, **not a byte copy**. To repair already-rendered footage, explicitly redraw both keyframes of the affected shot, review them, then regenerate its dependent clip. Updating only the first frame leaves its old end frame and clip inconsistent. Python changes require a fresh agent process; no automatic paid repair is performed.

## Chained keyframe continuity

- A project opts in with `frame_continuity.json` beside `render_acceptance.json`, containing `{"mode":"chained_keyframes"}`. Playback follows numeric camera order and each camera's stored active-shot order, not numeric shot IDs.
- Within the same camera, the preceding last frame becomes the next first frame byte-for-byte. A camera change generates a new view of that ending at the same instant, using it as a mandatory scene reference. Every new last frame uses its own first frame as a mandatory scene reference. Any assigned set references must also be approved inputs; remaining capacity goes to approved portraits, with newly entering characters prioritized.
- Ending changes invalidate only the directly dependent next shot's frame/clip reviews and final-film approval, without deleting its media or propagating through its unchanged ending. Timeline changes invalidate shots whose immediate predecessor changes, not the entire suffix.
- Replacing or changing a set reference invalidates only shots bound to that set and final-film approval. It does not alter shot-frame pixels or invalidate unbound successor shots.
- Chained reference selection follows explicit frame visibility, including entrances and exits; mentioning an offscreen person does not add their portrait. Unknown provider limits use a conservative budget, reserved for required set and scene inputs before optional portraits.
- Scoped rendering generates exactly the requested shots. Each uses its immediate playback predecessor's saved ending, or its fresh ending when both are requested. Saved endings remain usable even if their shot's approval or older incoming link is stale. Earlier ancestors are not inspected, and gaps between requested shots are allowed when their immediate inputs exist. Missing source endings still refuse generation before any image calls; no additional paid work is silently added.
- Film's still-generation decision checks only for missing immediate predecessor endings; it never forces prefix expansion. For example, generating Shot 5 uses Shot 4's saved last frame without regenerating Shots 1–4, even when Shot 3 needs review. Existing target-frame provenance/SHA256 checks still require an explicit redraw before replacing a target with mismatched cached source state. This preserves saved shots; it does not claim all earlier boundaries have been repaired.
- Chained mode requires a video provider with last-frame bracketing. First-frame-only models such as HeyGen are rejected with an actionable error rather than pretending an unused last keyframe enforces clip continuity. Keyframe boundaries are exact within a camera; actual video endpoints can still drift from their conditioning images.

## Assistant responsiveness

- Agent startup registers planning and rendering tools without importing their heavy pipelines, provider SDKs, or embedding/reranking dependencies. Those dependencies load when the corresponding operation is first used; generation still incurs its provider and pipeline costs.
- Assistant text is streamed from the provider through Python JSONL and SSE as it arrives, without simulated character-by-character replay. Each model pass has a stable sample ID; tool preambles and final answers stay separate. Tool activity remains in the Activity drawer. Streamed arguments never execute until the complete tool call has passed finish-reason and JSON validation.
- Interrupted responses retain their visible text with an explicit partial-response label; length-limited output is labelled **Response cut short**. A failure after published text does not retry the request or replay tools. Before output, the existing bounded transient-error policy owns retries; SDK retries are disabled. Malformed tool calls no longer fall back to an untooled request.
- Reconnection sends queue state and an authoritative current-turn snapshot, then reconciles completed history by turn/sample identity. It never restarts generation. Snapshots retain at most 32 sessions, 32 samples and 64 tool summaries per turn, with 128 KiB of text and a 192 KiB serialized-event limit. An overflow preserves the browser's partial text and displays a recovery notice until finalized history can replace it. SSE readers exceeding a 256 KiB writable-buffer limit are disconnected independently of the provider.
- Already-visible text survives a child-process exit in the open browser. Partial text is not journaled per delta: a hard server restart or a later turn superseding the in-memory snapshot can make an unpersisted partial unavailable to a newly opened page. Completed records remain authoritative.
- The first text update is immediate; later deltas are coalesced by animation frame with a 100 ms fallback and a bounded 256-event batch. Unchanged Markdown rows are memoized. Auto-scroll follows the bottom during layout, but leaves the reader in place when inspecting older messages. Phases distinguish queueing, context preparation, compaction, model waiting, responding, and tool execution.
- Assistant history is streamed from the global log and retains the latest 120 displayed messages, preserving their ordering and IDs. The backend caches up to 16 session-history projections and shares concurrent reads. Append, truncation, replacement, or rewrite invalidates the cache; changed logs are fully rescanned, so a cold read of a large log can still take seconds. Approval fingerprints are not cached by this mechanism.
- Tool results are delivered as soon as execution completes. The agent waits for either progress or completion instead of polling every 100 ms, and drains final progress before publishing the result.
- Context-budget checks count unchanged history and each appended tool/image message once per turn. Cached counts are removed with trimmed tool rounds, and history/system counts are rebuilt after compaction; thresholds, token-estimation rules, image observations, and authoritative records are unchanged. Counts are turn-local, not a persistent context cache. A controlled 20-round workload with 704k characters of history and a 200k-character image observation per round reduced profiled CPU time from 18.34 seconds to 2.14 seconds; these are local-loop measurements, not a promise of faster provider generation.
- The backend keeps one active request and a FIFO of pending messages, dispatching the next only when the active turn finishes. Page refresh restores active/pending rows without restarting the agent. **Stop**, agent replacement, or process failure marks affected messages **Cancelled**; pending requests are not persisted across a server restart. A planning operation that changes the active session cancels old-project follow-ups instead of sending them into the new project. Stopping locally does not guarantee cancellation of an already-submitted paid provider job.
- **Waiting for the queue-enabled bridge** prevents untracked submissions when the browser has reconnected to an older backend or has lost its event connection. Keep editing the draft; reconnect, or restart the web server after the current request finishes to load the updated bridge.
- Backend changes require a web-server restart after the current assistant request finishes. Python-only changes require a fresh agent process. Refreshing the browser does neither; do not stop an active planning or generation request to install an update.
- Planning failures report the underlying exception type and parser/validation detail, rather than only Tenacity's `RetryError` wrapper. Partial text artifacts remain available. An `OutputParserException` means a model response could not be parsed or validated; inspect its detail before retrying or changing the source script. Earlier wrapper-only failures do not contain the discarded response and cannot be diagnosed retrospectively from that message alone.
- Narrative planning defaults to a 16,384-token completion budget, including any tokens the provider counts toward completion generation. Override it with `VIMAX_NARRATIVE_MAX_TOKENS` (minimum 256). A provider response with `finish_reason: "length"` has exhausted that budget and can contain no visible JSON; this is not evidence that the source script is invalid. A larger budget can increase token costs on paid text models.

### Assistant performance diagnostics

- Python writes `.vimax/logs/agent_performance.runtime.jsonl`; Node and browser summaries use `.vimax/logs/agent_performance.jsonl`. Separate files give each rotating log one process owner. Runtime retention is 5 MiB plus one `.1` backup, with 16 KiB records; bridge retention is 1 MiB plus one `.1` backup, with 8 KiB records and at most 128 pending writes. These are diagnostic summaries, not per-token logs. A full telemetry queue drops metrics rather than blocking chat; write failures emit one bounded diagnostic and do not fail the turn.
- Join Python `turn_id`/`sample_id` with the bridge's `turn_id`, `messageId`, `sessionId`, and epoch. Request estimates include system messages, retained history, current-turn messages, and tool schemas. They are estimates, not billed usage. Actual prompt/completion/cache/reasoning counts remain null when unavailable; compaction requests are identified separately from conversational samples.
- Browser `firstVisibleTextMs` measures send to the first nonempty live row intersecting the conversation viewport on a rendered frame. `firstReceiptToCommitMs` measures first displayable SSE receipt to that same frame; both are frame/commit proxies, not proof of physical pixel display. `completionMs` ends at terminal observation, not at delayed metrics submission. Hidden/unopened conversations report `visible: 0` without invented visible-text latency. History/snapshot restoration is not a fresh model first token.
- `/api/agent-metrics` accepts only allowlisted numeric fields and known correlation IDs in an 8 KiB body. Content fields and oversized bodies are rejected; duplicate or unknown message correlations return 409. New performance records exclude prompts, answer text, tool arguments/results, images, credentials, and raw provider error bodies. Durations use each process's monotonic clock; do not subtract unrelated Python, Node, and browser clocks.
- `VIMAX_LLM_STREAM_INCLUDE_USAGE=1` requests optional streamed usage from a compatible provider; `0` disables that request option. It defaults on for `api.openai.com` and `openrouter.ai`, off for other hosts to avoid breaking OpenAI-compatible endpoints that reject optional fields. Returned usage is collected either way; unsupported or absent usage remains null.
- Local-only rollout measurements and exercised failure/recovery boundaries are recorded in [the streaming plan](ASSISTANT_STREAMING_PLAN.md#implementation-and-verification--2026-10-18). They are not paid-provider latency guarantees.
